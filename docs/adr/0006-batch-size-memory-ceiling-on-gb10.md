# Baseline train_step OOMs on GB10 at TrainConfig's batch_size=256; interim batch_size=16

Running the first real sanity check on the DGX Spark (GB10) surfaced two related problems at the default `TrainConfig.batch_size=256`, both traced to the same root cause: this 125M-param model, with no gradient checkpointing, mixed precision, or other memory-saving technique, needs far more peak memory for backward-pass activations at batch=256 than the naive numbers suggest.

**What happened:** a jitted gradient computation isolated from the rest of `train_step` (returning the full gradient pytree as an output, rather than fusing straight into an in-place optimizer update) failed to allocate GPU memory, backing off from 91GiB down through successive retries to 31GiB and still failing. The actual `train_step` (forward + backward + optimizer update fused into one `nnx.jit`-compiled function, allowing XLA to donate/reuse buffers far more aggressively) did not crash outright at batch=256 — but at that same memory ceiling, it silently produced NaN parameters after the very first step, with no error raised. Isolating whether this was a masking bug (ADR-adjacent fix already made once, see the causal-mask `-inf`-gradient issue in `layers.py`) or a memory issue: dropping to `batch_size=16` and re-running the identical (previously-NaN-producing) shape and step sequence produced finite loss and finite params throughout, including the two shapes that had triggered NaN at batch=256. This isolates the cause to memory pressure, not a remaining correctness bug in the loss/gradient computation itself.

**Why this happened:** a naive (no-checkpointing) transformer backward pass must retain every layer's intermediate activations (attention scores/weights, FFN hidden activations, etc.) simultaneously. At 12 layers, embed_dim=768, ffn_dim=3072, batch=256, and sequences up to 287 tokens, this adds up to tens of gigabytes even before accounting for optimizer state and XLA's own workspace overhead — enough to exceed what's actually available on GB10's unified memory once the OS, driver, and other overhead are accounted for.

**Interim decision:** `scripts/sanity_run.py` overrides `batch_size=16` to unblock a real end-to-end training check on hardware. This is *not* a fix for the actual experimental run — 16 is far below the batch size needed for stable, efficient training of a 125M-param model, and was chosen only to get comfortably clear of the observed memory ceiling for a short validation run.

**Resolution: gradient accumulation.** Of the candidates considered (gradient accumulation, activation checkpointing/rematerialization, mixed precision), gradient accumulation was chosen first. It carries no numerical risk — each micro-batch runs the same forward/backward math as today, just at a smaller batch, with the resulting gradients averaged before a single optimizer update — so it re-establishes a batch_size=256-equivalent training step on top of the already-verified batch_size=16 correctness, without introducing new failure modes (unlike bf16, which changes numerics, or rematerialization, which changes what's recomputed vs. stored) while the three model variants are still being independently trust-established. Mixed precision and activation checkpointing remain deferred; either may still be needed later for throughput, but they're follow-up efficiency work, not a prerequisite for a correct batch_size=256 step.

`TrainConfig` now has `grad_accum_steps: int = 16`, splitting the effective `batch_size=256` into 16 micro-batches of `micro_batch_size=16` (the value this ADR verified safe) — each run through its own forward+backward pass via `train_step_accum`, with gradients averaged (not summed) across the 16 passes before one `optimizer.update`, so `peak_lr` and the rest of the batch=256-tuned hyperparameters don't need re-tuning. See `train_step_accum` and `sample_training_microbatches` in `train.py`.
